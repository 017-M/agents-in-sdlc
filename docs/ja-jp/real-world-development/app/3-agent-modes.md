最初に、小さな機能をプロジェクトに追加しました。より大きな変更には、さらにしっかりしたプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue を使って新機能を生成するところから始め、コードが有効で、機能が期待どおりに動作することを確認し、最終的にプロジェクトへ正しくマージします。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは中心となる概念に集中できるように手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェントセッションを始めます。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増えてきたため、訪問者がゲームをカテゴリやパブリッシャーで絞り込めるようにします。バックログの Issue には機能の概要がありますが、複数のカテゴリを組み合わせる方法など、実装前に合意が必要な詳細もあります。Plan モードで方針を決めた後、範囲を明確にした実装を Autopilot に任せます。

## 背景

AI コーディングエージェントを開発フローに導入しても、開発の基本は変わりません。むしろ、より重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細を記載した Issue を開きます。
2. 実装する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションプロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや Organization によって異なりますが、多くの場合は上記の流れを基本にしています。

この標準的な手順に沿うことで、AI が生成したコードが要件を満たし、人間が作成したコードと同じレビューのプロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントにどこまで自律的に作業を任せるかを設定します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次に進む前に入力を待ちます。
- **Plan**: エージェントが先に計画を作成します。エージェントが実行する前に、計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律的に作業します。コードを作成し、テストを実行して、入力を待たずに作業を繰り返します。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。テンプレートに用意された既存の Issue なので、新しいものを作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数のカテゴリをどのように組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを終えるまで PR は作成しません。計画の修正は承認前に依頼し、後で検証できるよう Issue の URL と合意した追加事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認しただけでモードが自動的に切り替わるとは限らないため、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。作成した計画に沿ってコードを生成し、テストも実行しながら、作業を繰り返して進めます。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同様にマージ前にレビューします。コードを確認し、サイトを実行して問題がないことを確かめましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリとパブリッシャーの組み合わせも含め、結果を Issue と承認した追加事項に照らし合わせます。既存のリポジトリ指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、影響を受けるチェックを再実行します。Playwright の E2E 設定はビルド済みのプレビューを配信し、ローカルサーバーを再利用できます。以前のレッスンではなく、この worktree に属するサーバーをテストしていることを確認してください。

## 新機能を確認する

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択して、結果が一致することを確認します。フィルターを解除してから、パブリッシャーを選択し、該当する結果だけが表示されることを確認します。
4. カテゴリとパブリッシャーを組み合わせ、結果を Issue と承認済みの計画と照らし合わせます。複数カテゴリがサポートされる場合は、合意した組み合わせの動作を確認します。
5. 一致するゲームがない組み合わせを試して、空の状態を確認します。フィルターをクリアまたはリセットし、一覧全体に戻ることも確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンでも同じセッションを使う

フィルター機能の PR は、まだ作成またはマージしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次は、フィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションをそのまま残して、次のレッスンで再開します。

## まとめと次のステップ

さまざまなエージェントモードを使って、機能を構築してレビューしました。このレッスンでは、次のことを行いました。

- GitHub Issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動で検証しました。
